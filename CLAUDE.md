# LLM-AutoBench: контекст проекта для Claude Code

Этот файл читается автоматически при запуске Claude Code в корне проекта. Он заменяет историю прежних чатов (с Claude в браузере и с агентом Gemini в Antigravity). Всё важное из них собрано здесь.

## 1. Что это и зачем

Программный продукт для магистерской работы. Тема (формулировка руководителя):
"Дослідження ефективності застосування великих мовних моделей для автоматизації відповідей на типові запити користувачів".

Приложение: FastAPI + SQLite + одностраничный интерфейс (app/static/index.html, app/static/js/*.js, styles.css). Интерфейс на украинском. С автором общайся по-русски, строки интерфейса пиши по-украински.

В работе должно быть чётко видно две части:
- АВТОМАТИЗАЦИЯ: конвейер "запрос -> поиск знаний -> ответ модели -> решение об эскалации на оператора".
- ИССЛЕДОВАНИЕ ЭФФЕКТИВНОСТИ: эксперименты, измеряющие, насколько хорошо этот конвейер работает и сколько стоит.

### Замечания научного руководителя (обязательны к выполнению)
1. Тестировать модели в разных сферах, а не только в онлайн-банкинге.
2. Чёткая цель исследования с понятными результатами и выводами, а не цифры ради цифр.
3. Известный конечный потребитель: кто пользуется, для чего, чем помогает. Программа должна давать чёткий ответ под задачу пользователя.
4. Интерфейс менее вызывающий, как можно меньше признаков машинной генерации.
5. Пользователь может добавлять и тестировать собственные модели.

### Исследовательские гипотезы
- H1: лучшая модель зависит от предметной сферы.
- H2: стратегия промпта и качество найденного контекста влияют на результат не меньше, чем выбор модели.
- H3: для большинства типовых запросов достаточно дешёвой модели без потери безопасности.
- H4 (необязательная): влияние языка запроса (украинский и английский).
- Главный практический результат: каскадная маршрутизация. Простые запросы получает дешёвая модель, сложные или рискованные идут сильной модели или оператору. Экономию и влияние на безопасность считаем симуляцией на уже собранных данных без новых вызовов API.

### Целевые пользователи (для интерфейса и выводов)
- Руководитель поддержки: цена, риски, "какую модель взять".
- Инженер внедрения: детали метрик, настройка моделей и промптов.
- Студент и преподаватель: воспроизводимость, экспорт, объяснимость.

## 2. Структура кода

- app/main.py: маршруты API. app/config.py: константы методики, каталог провайдеров. Тесты подменяют каталог данных через LLM_AUTOBENCH_DATA.
- app/database.py: SQLite (data/llm_research.db), аддитивные миграции (PRAGMA user_version), таблицы domains, queries (variant_of, variant_type, lang), kb_documents, kb_chunks, query_gold_chunks, model_registry, model_status (check_kind), provider_status, model_daily_usage, evaluation_results, experiment_runs (corpus_version), judge_cache, seed_markers.
- app/domain_datasets.py, app/seed_data.py: сферы, запросы, шаблоны промптов P1-P5. Дополнительные запросы лежат в data/proposed/balanced_domain_queries_draft.json и загружаются один раз как чернетки.
- app/services: assistant.py (Помощник), retrieval.py (BM25 по корпусу знаний, corpus_mode kb или legacy), llm_runtime.py (клиенты и планировщик), model_discovery.py (поиск моделей и проверка каждой модели, фоновая задача с прогрессом), experiment_runner.py (серии), analytics.py, hypotheses.py (вердикты H1-H3), cascade.py, decision_support.py, kb_drafts.py (FAQ, чернетки, проверка), judge.py, evaluator.py, stats.py, export_service.py.
- app/static: index.html, js (core, home, providers, sandbox, assistant, experiments, analytics, results, dataset, settings), собранный tailwind.css (сборка в scripts/tailwind), chart.umd.js локально.
- Коды запросов: префикс сферы, категория, номер (FIN-INF-01, IT-NAV-02, EC-TRB-03, TL-CLR-01); перефраз получает суффикс -V1. Старые коды fintech (INF-01) переименовываются миграцией migrate_fintech_query_codes при старте.
- Отбор запросов в серию (select_stratified_queries): до N запросов на каждую пару (сфера, категория); если запросов больше, выбор случайный, но воспроизводимый (seed); equal_domain_sample выравнивает сферы по самой малой. Точный список кодов хранится в settings_snapshot серии (selected_query_codes), возобновление использует его. Прогноз (/api/experiments/estimate) вызывает ту же функцию.
- Реальный суточный лимит Gemini берётся из ошибки 429 (quotaValue) и сохраняется в реестре моделей с источником header.
- scripts/audit_dataset.py: аудит запросов (покрытие фактов, баланс, повторы, запросы, копирующие ответ). tests.py: pytest, 89 тестов (идут на реальной БД проекта, см. п. 4).
- Запуск на этой машине: python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 (run.bat ломается на кириллице в оболочке). Git есть, .env и *.db не отслеживаются.

## 3. Что уже сделано

Этап 1 (ядро):
- Единый JSON-контракт вывода {"answer","escalate","reason"} для всех стратегий P1-P5 (раньше эскалация определялась регулярным выражением, и FN-rate P1 = 100% был артефактом).
- Три условия контекста: no_context, gold_context, retrieved_context (поиск BM25).
- Q_det = 0.65*FC + 0.35*SS - 15*HR (веса и штраф в config.py), надёжность формата вынесена отдельно.
- Параметризованные сферы, таблица domains, API для добавления сферы.
- Серии и дооценка судьёй выполняются в фоне (раньше падали с ERR_NETWORK_IO_SUSPENDED).

Этап 2 (провайдеры):
- Реестр моделей в БД, форма "Додати модель" для любых OpenAI-совместимых API.
- 9 статусов по каждой модели (Працює, Немає зв'язку, Ліміт запитів, Денний ліміт вичерпано, Нульовий баланс, Невірний ключ, Ключ не задано, Модель недоступна, Не перевірено), классификация по HTTP-коду и структуре ошибки.
- Планировщик запросов (модель с исчерпанным суточным лимитом пропускается в серии, остальные идут дальше; серия получает статус paused_quota и продолжается позже), прогноз перед запуском (/api/experiments/estimate), цена "не задана" вместо $0.00.
- Исправлено дублирование логов (в интерфейсе блоки показывались по 3 раза).

Этап 3 (оценка и статистика):
- Устойчивость судьи к пустым и обрезанным ответам (повтор с большим лимитом токенов), независимость судьи (по умолчанию самооценка запрещена, флаг self_judged), единый судья в серии, проверка "эффекта потолка".
- Ручная разметка: экспорт и импорт CSV, каппа Коэна и Спирмен между судьёй и человеком.
- Единица анализа - запрос, повторы усредняются; Уилкоксон не считается при n<6; исправлены ДИ нулевой ширины и "Спільних пар: -"; матрица корреляций метрик; анализ чувствительности по весам и штрафу.
- Поля queries.source и review_status, стратифицированная выборка по сферам, аудит датасета.

Этап 4 (ноябрь 2026, подготовка финальных серий для главы 3):
- Надёжные статусы моделей и автопоиск, свои модели, оптимизация БД (WAL, внешние ключи, индексы, кэш судьи в БД), страница "Результати" по вопросам пользователя с вердиктами H1-H3, главная "Початок", мастер проверки гипотез, корпус знаний (один документ на запрос, без дистракторов), загрузка FAQ, проверка чернеток человеком, локальные Tailwind и Chart.js.
- Все 150 запросов утверждены (review_status = reviewed): fintech 60 manual, в каждой из трёх остальных сфер 16 manual и 14 llm_draft (подготовила модель, автор проверил и утвердил).
- Маршрутизация через OpenRouter: переключатель «Прямий API / OpenRouter» теперь есть и для Gemini; на карточках моделей, в списках выбора в экспериментах, в песочнице, помощнике и провайдерах стоит плашка «OpenRouter». Записи openrouter:* в реестре моделей получают цены из API OpenRouter.
- Цикл серии переписан (_run_series_cells): модели параллельно, каждая своей задачей; останов модели при лимите, отказе в доступе (ModelAccessError на 401/403) или 5 ошибках подряд, статус серии paused_quota, продолжение кнопкой «Довиконати»; сбой судьи не останавливает замеры. Ollama идёт по одной модели за раз, таймаут вызова 600 с (раньше 60 с ложно ставил статус «недоступна»). Повтор при 429/500/502/503/504/529. Для Groq лимит токенов в минуту автоматически уменьшает max_tokens.
- Прогресс по моделям (model_progress в /api/experiments, полосы в карточках серий) и статус серии на странице журнала.
- Эскалация берётся из поля escalate JSON (parse_method json, retry_json, json_direct, json_retry); ответ без валидного JSON считается переданным оператору (escalation_method = contract_violation). H2 исключает no_context из размаха. Стоимость: completion_tokens у OpenAI-формата уже включает токены рассуждений, поэтому output_tokens считается без них; для OpenRouter в cost_usd пишется фактически списанная сумма usage.cost.
- 16.11.2026 исправлена скорость «Результати»: бутстреп доверительных интервалов на чистом Python считал серию больше 8 минут и блокировал сервер; теперь векторный (numpy), расчёт серии 3-5 с, обе серии вместе около 9 с. Тяжёлые маршруты аналитики и гипотез сделаны обычными (не async) функциями, чтобы не блокировать цикл событий. Числа в сотых могут отличаться от прежних из-за другого генератора случайных чисел (зерно фиксировано, результат воспроизводим).

## 6. Стандарты кода

- Комментарии и docstring только там, где они объясняют "почему". Никаких декоративных заголовков вида "=== ... ===" и перечней "Принципы:" в docstring.
- Имена переменных и функций на английском, строки для пользователя на украинском, естественным деловым языком.
- Функции до примерно 50 строк, без лишних try/except "на всякий случай", без дублирования логики.
- Удаляй мёртвый код только после проверки, что на него нет ссылок.
- Миграции БД только аддитивные, старые данные не терять.
- Не создавай новых файлов без необходимости, не раздувай диффы переформатированием.

## 7. Правила работы (экономия лимита)

- Сначала план, потом правки. Для крупных задач использовать режим плана и согласовать его с автором.
- Не читай файлы из app/static/js и крупные модули целиком: ищи по имени функции или id (grep), читай небольшие диапазоны.
- После изменений запускай pytest tests.py. Не ослабляй и не удаляй тесты, чтобы они прошли.
- Не показывай и не коммить ключи из .env.
- Отчёт по задаче короткий: что изменено, как проверить, что осталось.

## 8. Честность результатов

- Не придумывай результаты экспериментов и не пиши выводы о превосходстве модели при малой выборке.
- Неизвестная цена модели не равна нулю.
- Автор должен суметь объяснить каждый модуль на защите, поэтому код должен быть понятным, а решения коротко обоснованными.

### 9.2 Как править записку (критично)
1. Перед правкой убедиться, что Word закрыт (иначе запись в docx падает; автор обычно держит файл открытым, попросить закрыть). Сделать резервную копию в scratchpad.
2. Править файл на месте. Не пересобирать его из body.txt, ch2.txt, build_thesis.py, insert_chapter.py, edit_all.py, fix_*.py, sources.py: они устарели и стёрли бы правки автора (титул, анотації, рисунки, его формулировки).
3. Инструмент: docs/thesis/docx_edit.py, класс Doc (sub по тексту с учётом разбиения на runs, rewrite, insert_after, insert_before, delete, сохранение). Скрипты запускать как `py -I`, путь к папке добавлять через sys.path. Правки без указания в списке не найденных (`d.missing`) считать неприменёнными. Скрипты-пакеты правок (edit_review.py и подобные) не перезапускать: вставки задвоятся.
4. Стили в docx: заголовки с id `1`, `2`, `3` (пункты третьего уровня нужны для оглавления), списки `Listdash`, подписи таблиц `Tablecaption`, рисунков `Figurecaption`, обычный абзац без стиля.
5. После правок: finalize_word.ps1 (Word COM: обновляет оглавление и поля, пишет PDF, печатает страницы заголовков), потом render_pdf.ps1 для просмотра страниц. Для зависшего экземпляра Word убивать только тот процесс, который запустили мы (по времени старта), не окно автора.

Оформление по Положению и методичке: A4, поля 25/10/20/20 мм, Times New Roman 14, интервал 1,5, абзац 1,25 см, без полужирного в тексте, нумерация страниц вверху справа (на титуле, задании, анотаціях и змісті не показывается), рисунки/таблицы/формулы нумеруются по разделам, разделы с новой страницы, таблицы не разрывать (у всех строк keepNext), перелик посилань по ДСТУ 8302:2015, номер по порядку первого упоминания.

### 9.4 Принятые решения по методике
- H3 оставлена как была: «для більшості типових запитів достатньо дешевої моделі без втрати безпеки». Известное несоответствие: правило проверки сравнивает среднюю якість, поэтому формулировка и критерий не вполне совпадают (автор отказался от замены 11.11.2026).
- H2: основной вердикт сравнивает размах Q по моделям, промптам и качеству контекста (найденный против эталонного). Режим «без контексту» только базовая линия, в вердикт не входит.
- Каскад (п. 2.5.2): консервативный базовый вариант; одно поле escalate выполняет две функции, это названо ограничением. Безопасная схема с escalate_to_model и escalate_to_human описана как направление развития, программа не менялась.
- Выбор модели: комплексное правило (допустимый FN, затем Q, затем более дешёвая замена в пределах 5 п.п. без большего FN, часть автоматических запросов показывается рядом). Qdet = оценка содержательного качества, не общая эффективность.
- Терминология: Φ = «показник відповідності формату вихідних даних» (не «надійність»); SS = Lexical Similarity (лексична близькість); HR = автоматичний індикатор непідтверджених числових і сутнісних згадок; FC не равно фактической корректности. LLM-AutoBench сравнивается с аналогами по трём группам функций (уже есть, настраивается, предмет разработки); новизна не в «ещё одном инструменте», а в методике комплексной оценки конвейера.
- Таблиця 1.7 (аналоги) сверена с документацией 08.11.2026: promptfoo присоединился к OpenAI (март 2026), HELM в режиме поддержки с июня 2026, Chatbot Arena теперь Arena; OpenAI Evals, lm-eval-harness, promptfoo, DeepEval, RAGAS, HELM, Arena. Добавлены τ-bench и RouteLLM.
