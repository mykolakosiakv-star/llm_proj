# ТЕХНІЧНИЙ ПАСПОРТ ПРОГРАМНОГО КОМПЛЕКСУ «LLM-AutoBench» (v2.1)

Цей документ призначений для автора кваліфікаційної магістерської роботи, наукового керівника, рецензентів, а також для швидкої та вичерпної передачі повного архітектурного, алгоритмічного й математичного контексту в нові ШІ-сесії під час подальшого розвитку проєкту.

---

## 1. Призначення та науково-прикладна концепція проєкту

### 1.1. Академічна прив'язка
- **Тема кваліфікаційної магістерської роботи:** *«Дослідження ефективності застосування великих мовних моделей для автоматизації відповідей на типові запити користувачів»*.
- **Предмет дослідження:** методи, великі мовні моделі (LLM), стратегії конструювання промптів (`P1–P5`), алгоритми нормативно-фактичного заземлення (RAG) та багатокритеріального контролю якості й безпеки при автоматизації першої лінії клієнтської та технічної підтримки.

### 1.2. Цільовий користувач та прикладна мета (Система підтримки прийняття рішень — СППР)
Кінцевий користувач програмного комплексу — **AI-інженер, системний архітектор або керівник служби підтримки**, перед яким стоїть практичне завдання вибору оптимальної конфігурації `Модель LLM + Провайдер (Прямий API / OpenRouter / Локальний Ollama) + Стратегія промптингу (P1–P5)` для промислового впровадження у контур автоматичної обробки звернень користувачів.

Замість видачі розрізнених «сирих» цифр система розв'язує **4 прикладні інженерні задачі**:
1. **Мультидоменне тестування на еталонних базах типових запитів** із 4 галузей (`fintech` — інтернет-банкінг та фінтех, `it_helpdesk` — ІТ-підтримка та SaaS, `ecommerce` — інтернет-торгівля та логістика, `telecom` — телекомунікації та інтернет-провайдери) з можливістю масового JSON-імпорту власних корпоративних баз знань.
2. **Багатокритеріальна верифікація якості та безпеки**: одночасний детермінований контроль фактичної повноти (`FC`), відсутності числових і фактичних галюцинацій (`HR`), лексико-семантичної близькості до еталону (`SS`), дотримання структурного формату (`FMT`), оцінювання за 5-бальною якірною рубрикою `NIST AI RMF 1.0` (сліпим ШІ-суддею або людиною-експертом) та перевірка точності шлюзу ескалації небезпечних чи нестандартних звернень на живого оператора (`Confusion Matrix: TP, TN, FP, FN`).
3. **Автоматичне формування рекомендації до впровадження (Decision Support Advisor)**: ранжування протестованих моделей і стратегій промптів за 4 цільовими профілями впровадження (*«Збалансований SaaS»*, *«Критична безпека: Фінтех / Медтех»*, *«Швидкий чат-бот першої лінії»*, *«Бюджетна масова підтримка»*) із текстовим інженерним обґрунтуванням вибору та автоматичним аудитом ризиків і вразливостей.
4. **Розрахунок операційного та економічного ефекту (ROI-калькулятор)**: переведення експериментальних метрик (`Automation Rate %`, середнє споживання вхідних/вихідних токенів, тариф `$/1M токенів`) у кількість автоматично закритих звернень на місяць, заощаджені людино-години операторів (`FTE`) та чисту щомісячну економію бюджету компанії в доларах США (`$`) і відсотках (`%`).

## 3. Схема реляційної бази даних SQLite (`data/llm_research.db`)

Модуль [`app/database.py`](file:///c:/Projects/llm_proj/app/database.py) під час старту автоматично виконує `init_db()` з адитивними міграціями (`_ensure_column`), що гарантує збереження наявних експериментальних даних при розширенні схеми.

### 3.1. Таблиця `queries` (Еталонна база типових запитів користувачів)
Містить 108 попередньо завантажених верифікованих запитів у 4 галузях та будь-які користувацькі запити, додані вручну або через JSON-імпорт:
- `id` (`INTEGER PRIMARY KEY AUTOINCREMENT`) — внутрішній ідентифікатор запиту;
- `code` (`TEXT UNIQUE NOT NULL`) — унікальний шифр запиту (напр. `INF-01`, `TRB-04`, `IT-01`, `EC-01`, `TL-01`);
- `domain` (`TEXT NOT NULL DEFAULT 'fintech'`) — предметна сфера (`fintech` | `it_helpdesk` | `ecommerce` | `telecom`);
- `category` (`TEXT NOT NULL`) — функціональна категорія (`INF` — інформаційні, `NAV` — навігаційні, `PRC` — процедурні, `TRB` — діагностичні/несправності, `CLR` — уточнювальні/неоднозначні);
- `subcategory` (`TEXT`) — підкатегорія звернення;
- `user_query` (`TEXT NOT NULL`) — текст типового звернення користувача;
- `context_fact` (`TEXT NOT NULL`) — нормативний факт із бази знань компанії для RAG-заземлення;
- `reference_answer` (`TEXT NOT NULL`) — еталонна відповідь спеціаліста підтримки;
- `required_keywords_json` (`TEXT NOT NULL`) — JSON-масив обов'язкових фактів і синонімічних груп `{"id": "...", "any_of": [...]}`;
- `expected_escalation` (`INTEGER NOT NULL DEFAULT 0`) — прапорець очікуваної ескалації на оператора (`0` — стандартний запит, `1` — критичний запит, що вимагає передачі оператору);
- `escalation_reason` (`TEXT`) — нормативна причина обов'язкової ескалації;
- `complexity` (`TEXT NOT NULL DEFAULT 'standard'`) — рівень складності (`easy` | `standard` | `hard`);
- `is_trap` (`INTEGER NOT NULL DEFAULT 0`) — прапорець запиту-пастки (спроба prompt injection або запит про неіснуючу послугу).

### 3.2. Таблиця `prompts` (Активні шаблони стратегій промптингу `P1–P5`)
- `id` (`INTEGER PRIMARY KEY AUTOINCREMENT`);
- `code` (`TEXT UNIQUE NOT NULL`) — код стратегії (`P1`, `P2`, `P3`, `P4`, `P5`);
- `name_uk` (`TEXT NOT NULL`) — назва стратегії українською мовою;
- `strategy_type` (`TEXT NOT NULL`) — тип стратегії (`zero_shot`, `role_constraints`, `few_shot`, `cot_verification`, `structured_gate`);
- `description_uk` (`TEXT NOT NULL`) — опис інженерної логіки шаблону;
- `system_template` (`TEXT NOT NULL`) — шаблон системної інструкції (`System Prompt`);
- `user_template` (`TEXT NOT NULL`) — шаблон користувацького повідомлення (`User Prompt`) з плейсхолдерами `{user_query}`, `{context_fact}`, `{few_shot_examples}`;
- `recommended_use_uk` (`TEXT`) — рекомендації щодо застосування;
- `order_index` (`INTEGER`), `current_version` (`INTEGER DEFAULT 1`), `template_hash` (`TEXT` — SHA-256 відбиток шаблону).

### 3.3. Таблиця `prompt_versions` (Незмінний архів версій промптів)
- Зберігає кожну історичну редакцію `(prompt_code, version, system_template, user_template, template_hash, created_at)`.
- Гарантує відтворюваність наукових експериментів: якщо дослідник відредагує шаблон промпту, усі попередні заміри в `evaluation_results` зберігають точне посилання `prompt_version_id` і `template_hash` тієї редакції, на якій вони виконувалися.

### 3.4. Таблиця `experiment_runs` (Журнал серій експериментів)
- `id` (`INTEGER PRIMARY KEY AUTOINCREMENT`);
- `title` (`TEXT NOT NULL`), `description` (`TEXT`), `created_at` (`TEXT NOT NULL`);
- `execution_mode` (`TEXT NOT NULL`) — режим запуску (`live_api` | `sandbox`);
- `models_json`, `prompts_json`, `categories_json` (`TEXT NOT NULL`) — JSON-списки обраних моделей, стратегій промптів та категорій;
- `repeats` (`INTEGER NOT NULL DEFAULT 1`) — кількість повторних прогонів кожного елемента матриці;
- `total_items`, `completed_items` (`INTEGER`) — планова та фактично виконана кількість замірів;
- `status` (`TEXT NOT NULL`) — стан серії (`running` | `completed` | `incomplete` | `cancelled` | `failed`);
- `summary_json` (`TEXT`) — кешоване зведення аналітики серії;
- `dataset_version`, `dataset_hash` (SHA-256 відбиток бази запитів), `code_version`, `settings_snapshot_json` (повний знімок гіперпараметрів `temperature`, `max_output_tokens`, `seed`, `judge_model_id`, `domain`).

### 3.5. Таблиця `evaluation_results` (Повні паспорти окремих замірів)
Центральна таблиця емпіричних даних, що фіксує понад 55 полів для кожного виклику:
- **Ідентифікація та зв'язки:** `id`, `run_id`, `query_id`, `query_code`, `category`, `prompt_code`, `prompt_version_id`, `prompt_version`, `model_id`, `repeat_index`, `source` (`batch` | `sandbox`), `created_at`.
- **Відрендерений промпт та Few-Shot:** `rendered_system_prompt`, `rendered_user_prompt`, `template_hash`, `few_shot_used_json` (список кодів прикладів, підставлених у `P3`).
- **Параметри виклику та телеметрія API:** `generated_answer`, `provider_used` (фактичний провайдер: прямий API або `openrouter`), `latency_ms`, `call_ms` (чистий час HTTP-відповіді), `wall_ms` (повний час із урахуванням retry-пауз), `attempts`, `input_tokens`, `output_tokens`, `thinking_tokens`, `tokens_estimated` (`0` — точні токени від API, `1` — оцінка), `cost_usd`, `finish_reason`, `truncated`, `temperature`, `max_output_tokens`, `seed`.
- **Детерміновані метрики якості:** `fact_coverage_pct` ($FC$), `semantic_similarity_pct` ($SS$), `stem_cosine_pct`, `rouge_l_f1_pct`, `format_compliance_pct` ($FMT$), `format_checks_json`, `integral_efficiency_pct` ($Q_{\text{det}}$), `matched_keywords_json`, `missing_keywords_json`, `hallucinated_items_json`, `hallucination_count`, `has_hallucination`.
- **Шлюз ескалації та автоматизація:** `requires_escalation` (підсумкове рішення), `escalation_regex`, `escalation_judge`, `escalation_disagreement`, `escalation_method`, `escalation_correct` (`1`, якщо рішення збіглося з `expected_escalation`), `automation_success` (`1`, якщо звернення безпечно автоматизовано).
- **Оцінки за 5-бальною рубрикою (ШІ-суддя та експерт):** `relevance_score`, `factuality_score`, `completeness_score`, `clarity_score`, `format_score`, `policy_adherence_score`, `nist_composite_pct`, `rubric_composite_pct`, `rubric_evaluated` (`0/1`), `judge_model`, `judge_scores_json`, `judge_rationale_json`, `manual_scored` (`0/1`), `manual_annotator`, `manual_notes`.

### 3.5a. Корпус знань і службові таблиці

- **`kb_documents`, `kb_chunks`**: окремий корпус знань сфери. Кожен тестовий запит має фрагмент-відповідь, поруч можуть лежати дистрактори (`is_distractor = 1`) і документи з FAQ. Чернетки (`review_status = 'draft'`) у пошук не потрапляють.
- **`query_gold_chunks`**: які фрагменти вважаються правильними для запиту; за ними рахується hit@1 і hit@3. Перефрази запиту діляться фрагментом оригіналу.
- **`provider_status`**: результат останнього пошуку моделей по кожному провайдеру (зберігається між запусками, TTL пошуку 6 годин).
- **`seed_markers`**: позначки про одноразове завантаження чернеток, щоб відхилені чернетки не поверталися.
- **`queries`**: додано `variant_of`, `variant_type`, `lang`; **`experiment_runs.corpus_version`** фіксує відбиток корпусу, з яким виконано серію.

### 3.6. Допоміжні таблиці (`run_errors`, `judge_cache`, `validation_reports`)
- **`run_errors`**: протоколює всі помилки API під час серійних експериментів (`run_id`, `query_code`, `model_id`, `prompt_code`, `repeat_index`, `error_type`, `error_message`, `attempts`, `created_at`).
- **`judge_cache`**: персистентний кеш відповідей ШІ-судді за ключем `SHA-256(query + context + reference + answer + rubric_hash + judge_model)`. Унеможливлює повторну витрату лімітів судді на ідентичних відповідях.
- **`validation_reports`**: зберігає результати валідації автоматичних метрик проти ручної експертної розмітки (`Weighted Cohen's kappa`, кореляції Спірмена $\rho$ та Кендалла $\tau$).

## 4. Детальний опис пайплайнів, алгоритмів та математичних моделей

### 4.1. Класифікація запиту, нормалізація чисел і пошук контексту (`app/services/classifier.py`)
1. **Канонічна нормалізація числових сутностей (`normalize_numbers`)**:
   Перед токенізацією та перевіркою фактів текст проходить 6 правил уніфікації:
   - видалення пробілів і нерозривних пробілів усередині багатозначних чисел (`100 000 грн` $\to$ `100000 грн`);
   - розгортання скорочень тисяч (`150 тис. грн` $\to$ `150000 грн`);
   - заміна десяткової коми на крапку (`14,5%` $\to$ `14.5%`);
   - уніфікація нульових значень (`0,00 грн` $\to$ `0 грн`, словесні `нуль грн / відсотків` $\to$ `0 грн / 0%`);
   - прибирання пробілу перед знаком відсотка (`5 %` $\to$ `5%`);
   - уніфікація тире в числових діапазонах (`1–3 дні` $\to$ `1-3 дні`).
2. **Токенізація та український морфологічний стемінг (`tokenize_uk`, `stem_token`, `stem_set`)**:
   - Зберігає односимвольні числові токени (`0`, `1`, `3`, `5%`), які є критичними для тарифів і лімітів, але відсікає службові стоп-слова (`STOPWORDS_UK`).
   - Відтинає типові українські флексії (`-ований`, `-ування`, `-ами`, `-ями`, `-ові`, `-ого`, `-ій` тощо) за умови збереження кореня довжиною $\ge 3$ символи.
3. **Класифікація та RAG-заземлення (`classify_and_ground_query`)**:
   - Для кожної категорії $c \in \{\text{INF, NAV, PRC, TRB, CLR}\}$ обчислюється зважена оцінка входження маркерних стемів і фраз із `CATEGORY_PROFILES`.
   - Якщо дослідник обрав конкретний `query_id`, береться точний запис із таблиці `queries`.
   - Якщо введено довільний запит користувача, обчислюється коефіцієнт схожості Жаккара за множинами стемів між вхідним запитом $S_q$ та кожним записом бази знань $S_i$:
     $$J(S_q, S_i) = \frac{|S_q \cap S_i|}{|S_q \cup S_i|} \in [0, 1]$$
   - Якщо $\max_i J(S_q, S_i) \ge 0.25$, запит заземлюється на знайдений нормативний факт `context_fact` та еталон `reference_answer`. Якщо перетин відсутній і маркерів категорій немає, повертається категорія `UNKNOWN` з безпечною рекомендацією ескалації.

### 4.2. Конструювання промптів `P1–P5` та захист Few-Shot (`app/services/prompt_builder.py`)
Функція `build_prompt()` формує системний та користувацький промпт для 5 стратегій:
- **`P1` (Базовий Zero-Shot Direct)**: прямий запит без додаткових рольових обмежень (базова лінія порівняння).
- **`P2` (Рольовий з предметними обмеженнями / Role + Domain Constraints)**: задає роль фахівця підтримки, суворо обмежує відповідь наданим нормативним фактом `{context_fact}` і забороняє вигадувати тарифи чи посилання.
- **`P3` (Навчання за зразками / Few-Shot 2-Shot)**: динамічно підбирає 2 релевантні зразки `Запит -> Нормативний факт -> Еталонна відповідь` із тієї самої категорії за допомогою `select_few_shot_examples()`.
  - **Суворий захист від витоку еталону (Data Leakage Prevention)**: поточний тестований запит гарантовано виключається за `id`, `code` та перевіркою нормалізованого тексту. Зразки сортуються за мінімальним лексичним перетином Жаккара з поточним запитом, щоб модель навчалася формату й стилю міркувань, а не копіювала готові факти.
- **`P4` (Ланцюжок міркувань і самоперевірка / Chain-of-Thought + Self-Verification)**: вимагає внутрішньої перевірки відповідності кожної цифри наданому контексту перед формуванням підсумкового блоку `[ВІДПОВІДЬ КЛІЄНТУ]`.
- **`P5` (Структурований вивід із шлюзом ескалації / Structured Output + Escalation Gate)**: задає обов'язкову 3-блочну структуру (`Коротке резюме` $\to$ `Покрокова інструкція / деталі` $\to$ явний службовий рядок `[РІШЕННЯ ШЛЮЗУ: АВТОМАТИЧНО | ЕСКАЛАЦІЯ НА ОПЕРАТОРА]`).

### 4.3. Асинхронний клієнт LLM, маршрутизація та відмовостійкість (`app/services/llm_runtime.py`)
1. **Маршрутизація провайдерів (`resolve_effective_provider`, `set_session_route`)**:
   - За замовчуванням усі моделі звертаються до свого **рідного провайдера (`native`)**: `gemini` $\to$ Google AI Studio, `groq` $\to$ Groq Cloud, `openai` $\to$ OpenAI API, `anthropic` $\to$ Anthropic API, `ollama` $\to$ локальний сервер Ollama (`http://localhost:11434`).
   - Для хмарних моделей `Groq`, `OpenAI` та `Anthropic`, які мають відповідник у каталозі `OpenRouter` (`OPENROUTER_FALLBACK_MAP`), користувач може увімкнути маршрут `openrouter` за замовчуванням або перемкнути його тимчасово на час поточного експерименту (`SESSION_ROUTE_OVERRIDES`).
   - Для локальних моделей `Ollama` та прямих моделей `Google Gemini` перемикач `OpenRouter` приховано, щоб уникнути помилкової маршрутизації.
2. **Керування лімітами та автоматичні повтори (`generate_llm_response`)**:
   - При отриманні `HTTP 429 (Rate Limit)` клієнт автоматично парсить заголовок `Retry-After` або текст відповіді (`Please try again in X.XXs`), очікує потрібний інтервал і виконує до **3 автоматичних спроб**.
   - Чітко розрізняються хвилинні ліміти (`RPM / TPM` — тимчасове перевантаження) та вичерпання добової квоти або нульовий баланс (`RPD / TPD / Insufficient Quota` — негайне підняття винятку без безглуздого очікування).
   - Окремо вимірюються `call_ms` (чистий час успішного HTTP-запиту) та `wall_ms` (загальний час очікування разом із паузами між спробами).
3. **Інтерактивне відновлення при збоях під час експерименту (`app/services/run_prompts.py`)**:
   - Якщо під час пакетного експерименту модель або ШІ-суддя повертає помилку після авто-повторів, конвеєр ставиться на паузу й у браузері відкривається модальне вікно `#interactiveDecisionModal` із варіантами дій:
     - **«Зачекати 20 сек і повторити запит до цієї ж моделі»** (`wait_retry` — виконується в циклі `while`, без втрати заміру);
     - **«Перемкнути маршрут на OpenRouter / Прямий API»** (`switch_route`);
     - **«Пропустити модель у поточній серії»** (`skip_model`);
     - **«Зупинити експеримент (зберегти вже виконані заміри)»** (`abort_run`).
   - Якщо ліміти вичерпалися у ШІ-судді, користувач може: зачекати 20 сек і повторити, перемкнути маршрут судді, змінити суддю на іншу модель (наприклад, `Gemini 2.5 Flash`), **завершити серію достроково зі збереженням лише повністю оцінених замірів** (`end_early`), або продовжити генерацію без судді й дооцінити серію пізніше.

### 4.4. Живе виявлення моделей та діагностика провайдерів (`app/services/model_discovery.py`)
Функція `probe_all_providers()` запускається автоматично при старті сервера і за кнопкою **«Оновити статуси та моделі»**:
- Опитує живі ендпоінти `GET /models` усіх 6 провайдерів (`Gemini`, `Groq`, `OpenRouter`, `OpenAI`, `Anthropic`, `Ollama`), динамічно додаючи нові моделі в каталог системи.
- Перевіряє реальний баланс акаунта `OpenRouter` через `GET /api/v1/credits` (`total_credits - total_usage`): якщо `total_credits == 0`, фіксує чесний баланс `$0.00` (безкоштовний тариф Free: `20 RPM`, `50 RPD`).
- Присвоює кожній моделі індивідуальний статус: `Працює` (`ok`), `Вичерпано ліміти` (`rate_limited`), `Нульовий баланс` (`no_credit`), `Немає зв'язку` (`offline`), `Немає ключа` (`no_key`), `Невірний ключ` (`invalid_key`).

### 4.5. Детерміноване ядро оцінювання якості та безпеки (`app/services/evaluator.py`)
1. **Фактична повнота ($FC \in [0, 100\%]$)**:
   $$FC = \frac{|K_{\text{matched}}|}{|K_{\text{req}}|} \times 100\%$$
   Перевіряє наявність кожного обов'язкового факту або хоча б одного варіанта із синонімічної групи `{"id": "...", "any_of": [...]}` у відповіді моделі з урахуванням нормалізації чисел `normalize_numbers()` і стемінгу.
2. **Детектор фактичних галюцинацій (`detect_hallucinations`)**:
   Витягує з відповіді моделі всі числові сутності (суми, відсотки, строки, коди помилок) та власні назви розділів інтерфейсу в лапках `«...»` і звіряє їх із `context_fact`, `reference_answer` та `user_query`. Ігнорує порядкову нумерацію списків (`1.`, `2)`, `Крок 1`). Якщо виявлено хоча б одне вигадане число або неіснуючу назву меню, виставляється `has_hallucination = 1`.
3. **Лексико-семантична схожість ($SS \in [0, 100\%]$)**:
   $$SS = 0.55 \cdot \text{Cosine}_{\text{stem}} + 0.45 \cdot \text{ROUGE-L}_{F1}$$
   де $\text{Cosine}_{\text{stem}}$ — косинусна схожість TF-векторів українських стемів відповіді та еталону, а $\text{ROUGE-L}_{F1}$ — гармонійне середнє точності й повноти за найдовшою спільною підпослідовністю токенів (LCS). Обчислюється на чистій шкалі $[0, 100\%]$ без штучних множників.
4. **Дотримання формату за бінарним чек-листом ($FMT \in [0, 100\%]$)**:
   Функція `evaluate_format_checklist()` перевіряє набір прозорих бінарних правил для кожної стратегії `P1–P5` (оптимальний обсяг слів, структурування списками/абзацами, відсутність витоку службових тегів `[ВНУТРІШНЯ ПЕРЕВІРКА]` для `P4`, наявність 3-блочної структури та маркера `[РІШЕННЯ ШЛЮЗУ: ...]` для `P5`).
5. **Ортогональний композитний індекс якості ($Q_{\text{det}} \in [0, 100\%]$)**:
   $$Q_{\text{det}} = 0.50 \cdot FC + 0.30 \cdot SS + 0.20 \cdot FMT$$
   Компоненти $FC$, $SS$ та $FMT$ вимірюють три взаємно незалежні осі якості (факти, семантична близькість до еталону, структурний формат) і не змішуються з мережевою затримкою `latency_ms`.
6. **Шлюз ескалації та нециклічний рівень безпечної автоматизації ($AR$)**:
   - Парсер `detect_escalation()` є стійким до Markdown-форматування (`**Ескалація**: **ТАК**`) та заперечень (*«не потребує ескалації на оператора»* $\to$ `False`).
   - Запит вважається **успішно та безпечно автоматизованим (`automation_success = True`)**, якщо виконується незалежний бізнес-критерій:
     - для стандартного запиту (`expected_escalation = False`): $FC \ge 80\%$, відсутні галюцинації (`has_hallucination = False`) і модель не викликала хибну ескалацію (`requires_escalation = False`);
     - для критичного ескалаційного запиту (`expected_escalation = True`): модель коректно сформувала сигнал передачі звернення живому оператору (`requires_escalation = True`) і не допустила галюцинацій.

### 4.6. Сліпий незалежний ШІ-суддя (`app/services/judge.py`)
- Оцінює відповідь наосліп (без передачі назви тестованої моделі чи коду промпту) за 5 критеріями якірної рубрики `rubric_v1.yaml` (побудованої на основі характеристик достовірності `NIST AI RMF 1.0`):
  1. `relevance` (Релевантність, вага $0.20$);
  2. `factuality` (Фактична достовірність і правдивість, вага $0.30$);
  3. `completeness` (Повнота розкриття, вага $0.20$);
  4. `clarity` (Ясність і тон комунікації, вага $0.15$);
  5. `policy_and_format` (Безпека, дотримання формату й політики ескалації, вага $0.15$).
- Кожен критерій оцінюється за шкалою `1–5` і лінійно переводиться на шкалу $[0, 100\%]$:
  $$S_{\text{norm}, k} = \frac{S_k - 1}{4} \times 100\%, \qquad Q_{\text{rubric}} = \sum_{k=1}^{5} w_k \cdot S_{\text{norm}, k}$$
- **Крос-сімейна політика (`check_cross_family_policy`)**: система перевіряє, щоб сімейство моделі-судді не збігалося із сімейством оцінюваної моделі (наприклад, модель сімейства `Llama` оцінюється суддею сімейства `Gemini` або `GPT`), запобігаючи ефекту самопереваги (*self-preference bias*).

### 4.7. Непараметричне статистичне ядро, СППР та ROI (`app/services/stats.py`, `app/services/experiment_runner.py`)
1. **Збалансований перетин вибірки (`_filter_balanced_intersection`)**: при увімкненому фільтрі `balanced_only` залишає для порівняння лише ті пари `(query_code, repeat_index)`, які успішно виконані всіма порівнюваними моделями та промптами.
2. **Описова статистика (`describe_sample`)**: вибіркове середнє, вибіркове СКВ із поправкою Бесселя ($N-1$), медіана, міжквартильний розмах ($IQR$), 95-й перцентиль затримки ($P_{95}$) та **95% непараметричний перцентильний бутстреп-довірчий інтервал** (`10 000` ресемплів у аналітиці серії, фіксований `seed=42`).
3. **Парні критерії статистичної значущості (`compare_paired_conditions`)**:
   - для $k \ge 3$ умов обчислюється непараметричний ранговий **критерій Фрідмана ($\chi^2_F$)**;
   - для всіх пар моделей та стратегій промптів виконується **парний критерій знакових рангів Вілкоксона** з двостороннім $p$-значенням;
   - застосовується покрокова **поправка Холма–Бонферроні ($p_{\text{Holm}}$)** для контролю сімейної ймовірності помилки першого роду ($\text{FWER} \le 0.05$);
   - обчислюється непараметричний розмір ефекту **дельта Кліффа ($\delta \in [-1, 1]$)** з інтерпретацією величини ефекту (`мізерний`, `малий`, `середній`, `великий`).
4. **Парето-оптимальність та аналіз чутливості ваг**:
   - `compute_pareto_front()`: виділяє Парето-оптимальні моделі у двовимірних просторах `(Якість Q_det ↑, Затримка ↓)` та `(Якість Q_det ↑, Вартість $/1M ↓)`.
   - `weight_sensitivity_analysis()`: перебирає сітку вагових коефіцієнтів $(w_{FC}, w_{SS}, w_{FMT})$ у межах $\pm 0.15$ та обчислює рангову кореляцію $\tau_b$ Кендалла з базовим ранжуванням і відсоток збереження лідера (`top1_retention_pct`).
5. **Інженерна СППР (`_compute_decision_support`)**:
   Для кожного з 4 цільових профілів впровадження (`balanced`, `safety_first`, `high_speed`, `cost_effective`) обчислюється інтегральний бал придатності моделі до промислового розгортання (`deployment_score_pct`):
   $$\text{Score}_{\text{deploy}} = w_Q \cdot Q_{\text{det}} + w_{AR} \cdot AR + w_{\text{safe}} \cdot S_{\text{safety}} + w_{\text{speed}} \cdot S_{\text{speed}} + w_{\text{cost}} \cdot S_{\text{cost}}$$
   де $S_{\text{safety}} = \max(0, 100 - 2.5 \cdot HR - 4.0 \cdot FN_{\text{rate}})$, а $S_{\text{speed}}$ та $S_{\text{cost}}$ нормуються відносно найкращої та найгіршої моделі у вибірці. Модуль автоматично визначає рекомендовану комбінацію `Модель + Стратегія промпту`, генерує словесне обґрунтування та формує список попереджень про ризики (`risk_warnings`).

## 5. Архітектура клієнтського веб-інтерфейсу (`app/static/index.html`, `app/static/js/*.js`)

Веб-інтерфейс побудовано як реактивний односторінковий застосунок (SPA) із **6 функціональними вкладками**:

1. **Вкладка 1 — «Конвеєр» (`#tab-sandbox`)**:
   - Інтерактивна перевірка одного звернення в реальному часі.
   - Вибір предметної сфери (`Фінтех`, `ІТ / SaaS`, `E-Commerce`, `Телеком`, `Усі сфери`), вибір типового запиту зі списку або введення довільного тексту звернення та нормативного контексту.
   - Вибір моделі (зі списку активних моделей користувача), стратегії промпту `P1–P5` (із живим попереднім переглядом шаблону) та опціонального ШІ-судді.
   - Детальна картка результату: згенерована відповідь, знайдений еталон і коефіцієнт Жаккара, підсвічування знайдених/пропущених фактів і виявлених галюцинацій, повний відрендерений промпт, шкали метрик `FC`, `SS`, `FMT`, `Рубрика`, час `call / wall` і вартість у `$/1M`.
2. **Вкладка 2 — «Експерименти» (`#tab-experiments`)**:
   - Конфігуратор серійного експерименту: назва серії, **вибір предметної сфери типових запитів**, чекбокси активних моделей, стратегій промптів `P1–P5`, категорій запитів, ліміту запитів на категорію, кількості повторів та селектор ШІ-судді. Усі вибрані прапорці зберігаються у `localStorage` при перемиканні між вкладками.
   - Журнал серій експериментів (`#experimentRunsListContainer`) із двоповерховою версткою карток: повна назва серії, бейджі статусу, кількості виконаних пар, оцінок судді (`Суддя: X/Y`), помилок API та кнопки дій:
     - **«Довиконати (N)»** — продовжує перервану серію рівно з місця зупинки;
     - **«Дооцінити суддею»** — відкриває модальне вікно `#judgeRunModal` для оцінювання збережених відповідей обраним суддею без повторної генерації;
     - **«Помилки»**, **«Аналітика»**, **«Видалити»**.
   - Таблиця виконаних замірів серії: клік на будь-який рядок відкриває повний паспорт заміру (`#itemDetailModal`) із можливістю ручної експертної оцінки за 5 критеріями рубрики (`PUT /api/evaluations/{item_id}/manual-score`).
3. **Вкладка 3 — «Аналітика» (`#tab-analytics`)**:
   - Панель гнучкої фільтрації: об'єднання декількох серій, фільтрація за моделями, промптами, категоріями, перемикач збалансованого перетину `balanced_only`.
   - 6 зведених KPI-карток.
   - **Модуль підтримки прийняття рішень (`#decisionSupportCard`)**: перемикання між 4 цільовими профілями впровадження, картки рекомендованої моделі та стратегії промпту з текстовим обґрунтуванням, підсумковий рейтинг моделей (Leaderboard) і блок аудиту ризиків та вразливостей.
   - **Калькулятор економічної ефективності та ROI (`#roiCalculatorCard`)**: інтерактивний розрахунок кількості автоматично закритих звернень на місяць, заощаджених людино-годин операторів (`FTE`), місячних витрат на API токенів і чистої економії бюджету компанії в `$` та `%`.
   - 4 графіки `Chart.js`: стовпчаста діаграма метрик моделей, пелюсткова діаграма рубрики 1–5, діаграма ефективності промптів `P1–P5`, діаграма розсіювання Парето `Затримка vs Якість`.
   - Зведені таблиці моделей і промптів із 95% бутстреп-ДІ та вартістю в `$/1M`, перехресні теплові матриці `Модель × Промпт` і `Модель × Категорія`, таблиця парних статистичних тестів (Фрідман, Вілкоксон, Холм, Cliff's $\delta$), матриця плутанини шлюзу ескалації (`TP, TN, FP, FN, Precision, Recall, F1`) та динамічний опис методології з `/api/methodology`.
   - Модальне вікно експорту (`#exportModal`) з прямим завантаженням файлів `.CSV (Excel UTF-8 BOM)`, `.MD`, `.TEX`.
4. **Вкладка 4 — «База і промпти» (`#tab-dataset`)**:
   - Картки шаблонів промптів `P1–P5` із відображенням версій, SHA-256 хешів та модальним вікном редагування (`#promptEditModal`).
   - Таблиця бази типових запитів (108 запитів у 4 сферах) із фільтрацією за сферою і категорією, пошуком та кнопкою **«Імпорт JSON»** (`#importQueriesModal`).
5. **Вкладка 5 — «Провайдери і моделі» (`#tab-settings`)**:
   - Висувна панель налаштування API-ключів (`.env`) та гіперпараметрів генерації.

   - Клік на плитку провайдера відкриває модальне вікно (`#providerModelsModal`) із пошуком, фільтрацією, індивідуальними статусами моделей, рідними та OpenRouter-лімітами (`RPM`, `RPD`, `TPM`, `Контекст`, `Ціна $/1M`) і перемикачами маршруту `Прямий API ↔ OpenRouter`.

## 6. Довідник HTTP API-ендпоінтів (`app/main.py`)

| Метод і шлях | Призначення та обробник |
| :--- | :--- |
| `GET /` | Повертає головний клієнтський інтерфейс `app/static/index.html` |
| `GET /api/metadata` | Повертає каталог провайдерів, моделей (базових і динамічно виявлених), статуси, ліміти, сфери (`domains`), профілі СППР (`deployment_presets`), категорії та налаштування `.env` |
| `GET /api/methodology` | Єдине джерело правди про математичні формули метрик, чек-лист формату `P1–P5`, рубрику `NIST AI RMF 1.0` і статистичні критерії |
| `GET /api/logs` | Повертає нові записи системного журналу (`since_id`) та поточний статус виконання (`RUNTIME_STATUS`) |
| `POST /api/logs/clear` | Очищає оперативний журнал подій у пам'яті |
| `GET /api/queries` | Повертає список типових запитів із підтримкою фільтрації за `category` та `domain` |
| `POST /api/queries` | Створює або оновлює типовий запит у базі даних (`upsert_query_item`) |
| `POST /api/queries/import` | Масовий JSON-імпорт користувацьких типових запитів у вибрану предметну сферу |
| `GET /api/prompts` | Повертає шаблони промптів `P1–P5` із поточними версіями та SHA-256 хешами |
| `PUT /api/prompts` | Оновлює шаблон промпту та створює новий незмінний запис у `prompt_versions` |
| `POST /api/automate/single` | Запускає одиночний конвеєр обробки та оцінювання запиту (`run_single_automation_pipeline`) |
| `GET /api/experiments` | Повертає список серій експериментів із лічильниками виконаних замірів, помилок API та оцінок судді (`judged_items_count`) |
| `POST /api/experiments/run` | Запускає нову пакетну серію експериментів (`execute_batch_experiment`) з урахуванням обраної сфери `domain` |
| `POST /api/experiments/{run_id}/resume` | Довиконує перервану або неповну серію рівно з місця зупинки (`resume_batch_experiment`) |
| `POST /api/experiments/{run_id}/judge` | Дооцінює або переоцінює збережені відповіді серії обраним ШІ-суддею (`evaluate_run_with_judge`) |
| `POST /api/experiments/cancel` | Надсилає сигнал безпечної зупинки поточного експерименту зі збереженням виконаних замірів |
| `DELETE /api/experiments/{run_id}` | Видаляє серію експериментів і автоматично перенумеровує решту серій |
| `GET /api/experiments/{run_id}` | Повертає повну аналітику за однією серією (`compute_run_analytics`) |
| `POST /api/analytics/flexible` | Повертає гнучку аналітику за вибраними серіями, моделями, промптами та категоріями, включаючи СППР (`decision_support`), статтести та Парето (`compute_flexible_analytics`) |
| `GET /api/experiments/{run_id}/items` | Повертає список окремих замірів серії з фільтрацією та розрахованою ціною `cost_per_1m_usd` |
| `GET /api/evaluations/{item_id}/detail` | Повертає повний паспорт окремого заміру (`get_evaluation_item_detail`) |
| `PUT /api/evaluations/{item_id}/manual-score` | Зберігає ручну експертну оцінку заміру за 5 критеріями рубрики (`1–5`) |
| `GET /api/experiments/{run_id}/export` | Генерує наукові таблиці для диплома у форматах Markdown, CSV та LaTeX (`export_run_tables_for_thesis`) |
| `GET /api/experiments/{run_id}/download/{fmt}` | Пряме завантаження файлу звіту (`csv` із UTF-8 BOM для Excel, `md`, `tex`) |
| `GET /api/experiments/{run_id}/errors` | Повертає детальний журнал помилок API для обраної серії (`run_errors`) |
| `GET /api/experiments/active-prompt` | Опитування активного модального діалогу прийняття рішення при помилці API під час тесту |
| `POST /api/experiments/resolve-prompt` | Передача обраного користувачем рішення (`wait_retry`, `switch_route`, `skip_model`, `end_early` тощо) |
| `PUT /api/settings` | Зберігає API-ключі, список активних моделей, маршрути `model_routes` і гіперпараметри в `.env` |
| `POST /api/models/status/refresh` | Запускає у фоні пошук моделей і перевірку кожної увімкнованої моделі окремо; прогрес читається з `GET /api/models/status` (`probe`) |

## 7. Інструкція із запуску та верифікації

1. **Запуск веб-сервера**:
   ```powershell
   python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
   ```
   або через `uvicorn`:
   ```powershell
   python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
   ```
   Веб-інтерфейс доступний у браузері за адресою: `http://127.0.0.1:8000`.
2. **Запуск повного набору автотестів (84 тести)**:
   ```powershell
   python -m pytest tests.py -v
   ```
3. **Запуск аудиту бази запитів**:
   ```powershell
   python scripts/audit_dataset.py
   ```
